03

왜 같은 digest가 나올 수 있나

UAT와 prod는 버전이 다르다 — 1.3.0-rc.1과 1.3.0. 그런데도 이미지가 같다. 설계를 그렇게 잡았기 때문이다.

버전은 이미지 안에 넣지 않는다. 버전 문자열을 이미지에 박아 두면 코드가 똑같아도 버전이 다르면 이미지가 달라진다. 그러면 “UAT에서 검증한 그 이미지가 그대로 나갔다”를 digest로 증명할 방법이 없어진다. 그래서 이미지는 자기 버전을 모르는 채로 만들고, 컨테이너를 띄울 때 APP_VERSION으로 알려준다. 같은 이미지가 UAT에서는 1.3.0-rc.1, prod에서는 1.3.0이라고 자기를 소개하지만 이미지는 한 개다 — 태그만 두 개 붙어 있을 뿐이다.

구현은 두 조각이다. 앱은 환경변수를 1순위로 읽고, 워크플로가 실행 시점에 넘긴다.

// Version.java — 주입값 > jar 내장 version.yml > unknown
String injected = System.getenv("APP_VERSION");

# uat / prod 워크플로 — 빌드가 아니라 실행할 때 넘긴다
docker run --rm \
  -e APP_ENV=prod \
  -e APP_VERSION="${VERSION}" \
  -e APP_COMMIT="${BUILD_SHA}" \
  -e APP_sha256:dd51881f7da46d859df511e796c39a29d3b0b48741daf68ad9b0f0be184e487f="${sha256:dd51881f7da46d859df511e796c39a29d3b0b48741daf68ad9b0f0be184e487f}" \
  "${IMAGE}:${IMAGE_TAG}"
복사한 게 아니라 따로 만들었는데 같았다. prod는 이미지를 다시 빌드했다. 그 결과 바이트가 UAT 것과 같아서 두 태그가 레지스트리에서 같은 digest를 가리키게 됐다. 태그를 옮겨 단 것이었다면 이 값은 아무것도 증명하지 못한다.
이번 사이클에서 한 번 더 확인됐다. 조립 방식을 고쳐(--no-ff) release를 다시 만들자 커밋이 4dd91ac → 4448e5a로 바뀌었다. digest는 dd51881f… 그대로였다. 커밋 그래프가 달라져도 트리가 같으면 산출물이 같다.
04

조립 PR 1건 = 배포 1회

v4에서 prod 트리거는 pull_request closed(merged)다. 그래서 feature별로 PR을 따로 올리면 배포가 N회 돈다. 묶음 배포는 조립 브랜치를 만들어 PR 1건으로 올린다.

merge 직전

$ gh run list --workflow=prod-build-deploy.yml | wc -l
1

PR #6 merge 직후

$ gh run list --workflow=prod-build-deploy.yml | wc -l
2      ← 정확히 1회만 증가

조립 PR은 feature 2개를 담았지만 배포는 1회였다. concurrency는 동시 실행을 줄 세울 뿐 횟수를 줄이지 않는다 — 그래서 “PR 1건” 자체가 규칙이어야 한다.

정합성 검증 (v4 4.1절)

조립 브랜치는 release-0819와 내용이 같아야 한다. 다르면 충돌을 다르게 푼 것이다.

$ git diff release-0819 assemble/0819
(출력 없음)

$ git rev-parse release-0819^{tree} assemble/0819^{tree}
6b506c2e254f2bd1704933eb53afd5c1e5ab5fcd
6b506c2e254f2bd1704933eb53afd5c1e5ab5fcd     ← 동일
merge commit 가드도 돌았다. prod 워크플로가 master tip의 부모 수를 세어 Squash/Rebase merge를 잡아낸다. 레포 설정에서도 Squash/Rebase를 비활성화해 뒀다(09절). 
✅ merge commit (부모 2개) — same-SHA 유지
✅ digest 일치 — UAT(uat-v1.3.0-rc.1)에서 검증한 이미지가 그대로 나간다
05

충돌은 한 번만 풀었다

FeatureRegistry.register()는 의도된 충돌 지점이다. 세 기능이 모두 같은 자리에 한 줄씩 추가하므로 반드시 부딪힌다. v4는 같은 feature를 목적지마다 따로 merge하므로, “그러면 충돌도 목적지 수만큼 푸는 거냐”가 가장 흔한 반박이다.

merge목적지충돌 처리
4006 ← 첫 충돌dev사람이 해결 (1회)
4006test (PR #4)✓ rerere 자동 재적용
4006release-0819✓ rerere 자동 재적용
4006assemble/0819✓ rerere 자동 재적용
 
CONFLICT (content): Merge conflict in .../com/ti/FeatureRegistry.java
Resolved '.../FeatureRegistry.java' using previous resolution.

사람이 푼 건 1회고 나머지 3곳은 자동이었다. 그 결과가 같은지는 느낌이 아니라 tree SHA 일치로 확인된다(04절).

그래서 충돌 PR은 GitHub 버튼으로 못 닫는다. rerere 캐시는 클론 로컬에만 있어 GitHub 서버가 쓸 수 없다. PR #4·#5는 실제로 이렇게 막혔다. 
$ gh pr view 4 --json mergeable,mergeStateStatus
mergeable=CONFLICTING   state=DIRTY

$ gh pr merge 4 --merge
X not mergeable: the merge commit cannot be cleanly created.
로컬에서 풀어 push하면 GitHub이 그 PR을 MERGED로 자동 처리한다. 이것이 v4에 “한 기능의 merge는 담당자가 4곳 다 한다”는 규칙이 있는 이유다 — .git/rr-cache/는 push·pull로 전파되지 않는다.

07

기록해 둔 값이 실제로 움직였다

빌드 입력을 고정하지 않고 기록하기로 한 설계가 이번에 처음으로 값을 했다. 0818 사이클과 비교하면 두 개가 움직였다.

입력0818 사이클0819 사이클
빌드 JDK17.0.20+8-LTS 17.0.20.1+10-LTS
base 이미지 digestsha256:56cd3dfd… sha256:cbc584b3…
Gradle8.138.13
이게 왜 중요한가. 사이클 안에서는 UAT와 prod가 몇 분 차이라 같은 값으로 빌드된다 — 그래서 digest가 맞았다. 그런데 사이클 사이에는 움직인다. 만약 UAT와 prod 사이에 JDK가 바뀌었다면 digest가 어긋났을 것이고, 배포 원장에 두 값이 남아 있으므로 무엇이 움직였는지 지목할 수 있다. 고정(prevention)이 아니라 감지(detection)를 택한 이유가 이것이다.
08

샌드박스와 실전의 차이

샌드박스는 조직 레포에 올려 실전과 최대한 같은 조건으로 맞췄다. 남은 차이는 두 줄뿐이고, 둘 다 이유가 분명하다.

항목샌드박스실전 image-trial-server
이미지jib → ghcr, 이동 태그 + 불변 태그 병행동일
digest 출처docker inspect --format='{{index .RepoDigests 0}}'동일 명령
버전 발급conventional-changelog-action동일
브랜치 보호실전 설정을 복제. 스크립트로 as-is ↔ v4 전환원본
base 이미지공개 이동 태그사내 base, 역시 이동 태그
배포 대상 러너에서 docker run 1회 self-hosted 러너 + Blue-Green + ALB 전환
릴리스 봇 권한 GITHUB_TOKEN — 브랜치 보호를 우회하지 못한다 org GitHub App 토큰으로 우회
봇 권한이 왜 남은 차이인가. 실전은 릴리스 봇이 org GitHub App 토큰으로 보호를 우회해 chore(release) 커밋을 master에 push한다. 샌드박스는 그 앱의 private key가 없고, GITHUB_TOKEN(github-actions[bot])은 우회 허용 목록에 등록조차 되지 않는다 — API가 조용히 무시한다(확인함). 그래서 샌드박스는 master의 PR 요구만 뺀 별도 프로필로 돌린다.

빌드 입력 중 무엇이 움직일 수 있나

실전 image-trial-server를 실제로 확인한 결과다.

입력고정돼 있나
Gradle 의존성고정 — 동적 버전(+, latest, 범위) 없음
base 이미지실질 고정 — ti-server-base:java17-gdcm은 어느 워크플로도 재빌드하지 않는다. digest가 아니라 태그로 참조하므로 레지스트리가 불변을 보장하진 않는다 — 관행이지 규칙이 아니다
빌드 JDK고정 아님 — java-version: '17'은 최신 패치로 해석된다 (실행 로그: Resolved latest version as 17.0.20+8.1). corretto 배포판은 setup-java에서 major 버전만 지정할 수 있어 패치 고정이 아예 불가능하다

그래서 고정하지 않고 기록한다

JDK를 고정하면 CVE 패치를 자동으로 못 받는다. 그래서 고정(prevention) 대신 감지(detection)를 택했다 — 빌드 JDK와 Gradle 버전을 배포 원장에 남기고, digest가 어긋나면 무엇이 움직였는지 지목한다.

소스 트리가 다르다

UAT 태그가 가리키는 트리 SHA ≠ prod 빌드 커밋의 트리 SHA. 조립 이후 코드가 바뀐 것 — 가장 심각한 경우다.

빌드 JDK가 움직였다

트리는 같은데 기록된 JDK가 다르다. 소스는 그대로이고 컴파일러만 바뀐 것.

기록 안 된 변수가 움직였다

트리도 JDK도 같은데 digest가 다르다. base 이미지 등 아직 기록하지 않는 입력을 의심한다.

UAT 미경유

이 버전으로 UAT에 올린 기록 자체가 없다. v4 금지규칙 7 위반.

이 4가지 분기를 실제 태그를 대상으로 전부 돌려 확인했다. digest가 갈리는 것은 결함이 아니라 측정값이다 — 갈렸다는 사실과 그 원인이 곧 알아야 할 정보다.

설정실전 현재v4 요구
Squash merge허용비활성
Rebase merge허용비활성
master required_linear_history 켜짐 꺼야 함

required_linear_history 는 “merge commit 금지” 다. v4 금지규칙 8(“모든 merge는 Merge Commit”)과 정반대다. 그런데 master에는 merge commit이 실제로 존재한다 — enforce_admins 가 꺼져 있어 관리자만 우회해 merge commit을 만들고 있는 상태로 보인다(이 인과관계는 추정이다). 일반 개발자가 v4대로 merge하면 막힐 가능성이 높다.

순서가 정해져 있다 — 422를 맞고 알아낸 것

required_linear_history 가 켜진 상태에서는 squash/rebase를 끌 수 없다.

PATCH /repos/{owner}/{repo}  {"allow_squash_merge": false, "allow_rebase_merge": false}

422 Validation Failed
  Sorry, you need to allow either squash or rebase merge strategies, or both.
  (protected_branch_policy)

linear history가 merge commit을 막고 있는데 squash/rebase까지 끄면 병합 수단이 하나도 안 남기 때문이다. 그래서 전환 절차서에는 순서를 명시해야 한다.

v4로 갈 때

1. master 브랜치 보호에서 required_linear_history 끄기
2. 그 다음 Squash / Rebase merge 비활성

되돌릴 때

반대 순서. 1. Squash / Rebase 먼저 켜고
2. 그 다음 required_linear_history 켜기

샌드박스에는 두 상태를 오가는 스크립트를 넣어 뒀다 — ./scripts/repo-settings.sh as-is 로 실전의 지금 상태를 재현하고, to-be 로 v4 상태로 넘긴다. 왕복 전환을 반복 실행해 멱등한지 확인했다. 발표 중에 실제로 막히는 것과 풀리는 것을 라이브로 보여줄 수 있다.
샌드박스에는 프로필이 하나 더 있다 — solo. 실전은 릴리스 봇이 org GitHub App 토큰으로 보호를 우회해 chore(release) 커밋을 master에 push한다. 샌드박스에는 그 App의 private key가 없고 GITHUB_TOKEN은 우회 허용 목록에 등록조차 되지 않는다. 그래서 solo = to-be에서 master의 PR 요구만 뺀 프로필로 파이프라인을 끝까지 돌린다. App 시크릿이 준비되면 to-be로 넘어간다 — 위 표의 3개 설정은 세 프로필 모두 동일하다.

이번 사이클에서 문서를 고칠 것

샌드박스의 산출물은 배포가 아니라 문서 교정이다. 이번에 한 건 나왔다.

F5 — orphan 검출 명령이 배포 전에는 거짓 양성을 낸다

4.1절 배포 전 체크에 적힌 명령을 그대로 돌리면 정상 사이클에서도 2건이 잡혔다. release 직접 커밋이 아니라 feature 커밋 그 자체였다 — 배포 전이라 master가 아직 안 받았으니 당연히 걸린다.

# 문서 (배포 전에 쓰면 거짓 양성)
git log release-0819 --not master --no-merges
  cb83251 feat: IMTDEV-4005 …      ← feature 커밋
  692eaf6 feat: IMTDEV-4006 …      ← feature 커밋

# 교정 — 이번 배포분 feature 도 제외한다
git log release-0819 --not master <feature들> --no-merges
  (출력 없음)  ✓

교정본으로 release에 직접 커밋을 하나 만들어 재실행하니 그것만 잡혔다. 경고가 늘 뜨면 아무도 안 본다 — 그래서 이건 고쳐야 한다. /imt-status 스캔도 같이 교정했다(release- 브랜치 누락 + 규칙 번호 7→6).
