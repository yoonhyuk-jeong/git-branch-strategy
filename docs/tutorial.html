v4 실습 가이드 — 조직 샌드박스에서 직접 돌려 보기

이 문서는 읽는 문서가 아니라 실행하는 문서다. 순서대로 하면 v4 플로우가 한 바퀴 돈다. 망가뜨려도 된다 — 이 레포는 그러라고 있다.

  • 규칙 원본(단일 진실): Confluence — IMT Git Branch 전략 v4
  • 검증 현황과 문서 교정 발견(F1~F13): TESTING_V4.md
  • 발표용 시각 자료: https://yoonhyuk-jeong.github.io/git-branch-strategy/

이 문서를 읽는 법 — agent workflow가 정상 경로다

각 단계는 이렇게 생겼다.

Claude Code slash command / Codex skill — 팀원이 실제로 쓰는 workflow다. Claude Code에서는 /imt-*, Codex에서는 $imt-*로 실행한다. Codex의 /skills에서도 선택할 수 있다.

속을 보는 법 — 그 workflow가 내부에서 하는 일. <details> 로 접어 뒀다. 원리를 이해할 때만 펴 본다.

raw git 명령을 외우려 하지 말 것. agent workflow가 네이밍 검증·분기원 확인·orphan 검출·정합성 판독· 승인 게이트를 대신 해 준다. 손으로 하면 그걸 다 빼먹는다. 실제로 이 문서를 만드는 과정에서 검증자가 손으로 돌렸다가 --no-ff 를 빠뜨렸고, 잘못된 브랜치에 커밋했고, 판독 명령을 틀리게 썼다.

Claude Code Codex 인자 언제
/imt-status $imt-status — 지금 뭐가 어디까지 갔나. 아무 때나, 제일 먼저
/imt-feature $imt-feature <JIRA> <기능명> [MMDD] [이니셜] 새 기능 시작
/imt-test $imt-test — (현재 feature 에서) QA 준비 → test PR + 배포
/imt-release $imt-release [MMDD] [feature...] 배포일 확정 → UAT 조립
/imt-deploy $imt-deploy [release-{날짜}] UAT 통과 → prod
/imt-sync $imt-sync [feat|env] feat: 내 브랜치 최신화 / env: 배포 후 정리·환경 최신화

강제의 한계. 이 workflow는 Claude Code나 Codex를 통할 때만 유효하다. 터미널에서 직접 git push 하거나 GitHub UI 에서 Squash 버튼을 누르는 건 못 막는다. 진짜 강제는 레포 설정 (Squash/Rebase 비활성, 브랜치 보호)이고, agent workflow는 "올바른 길을 가장 쉬운 길로" 만드는 계층이다.

0. 준비 (한 번만)

cd ~/solutions/git-branch-strategy      # 경로는 각자 환경에 맞게
gh repo view trial-informatics/git-branch-strategy-sandbox --json name,visibility
git config --global rerere.enabled true   # v4 에서는 필수 — 같은 feature 를 4곳에 merge 한다
./scripts/repo-settings.sh show

show 출력이 아래와 같아야 정상 진행된다.

merge=true  squash=false  rebase=false      ← 금지규칙 8 (Merge Commit 만)
master  PR 필수 : no                        ← solo 프로필
        linear history : false              ← v4 는 false 여야 한다
test    PR 필수 : YES / force push 허용 : false

다르면 ./scripts/repo-settings.sh solo.

to-be 는 실전과 동일한 목표 상태인데 master 에 PR 을 요구한다. 그러면 릴리스 봇 (GITHUB_TOKEN)이 chore(release) 커밋을 master 에 못 넣어 파이프라인이 끊긴다. 실전은 org GitHub App 토큰으로 우회하지만 샌드박스에는 그 키가 없다.

실습용 시작점 확인

이 레포는 실습용으로 정리된 시작점이다. 아래 결과가 나오면 준비가 끝난 상태다.

git fetch origin --prune --tags --quiet
git branch -r --list 'origin/*'                               # dev, master, test만 존재
git rev-list --left-right --count origin/master...origin/test # 0  0
git rev-list --left-right --count origin/master...origin/dev  # 0  0
grep '^version:' version.yml                                  # version: 1.5.0
ls .git/rr-cache 2>/dev/null | wc -l                          # 0

시작점 태그는 practice-start-20260819다. 실습 후 원상 복구 절차는 10절을 따른다. uat-v*·v* 배포 태그와 archive/* 정리 증적은 삭제하지 않는다.

1. 먼저 "지금 상태 읽는 법"

v4 에서 가장 중요한 기술은 명령을 치는 게 아니라 "이 기능이 어디까지 갔나"를 읽는 것이다.

Claude Code / Codex

/imt-status    또는    $imt-status

지금 실행하면 feature 브랜치가 없어서 칸반이 비어 있다. 실습을 진행하면 이런 식으로 채워진다.

0821/YH/IMTDEV-5001-audit-filter      dev test master
0821/YH/IMTDEV-5002-a                 dev(구버전) test        ⚠ 재병합 필요
0821/YH/IMTDEV-5003-b                 test                    ⚠ master 뒤처짐 → /imt-sync feat

읽는 법:

패턴 해석 다음
dev 만 개발/연동 중 준비되면 /imt-test
test, release 없음 QA 중 또는 QA통과·배포일 미정 = 대기 확정 시 /imt-release
test release UAT 검증 중 = 이번에 나갈 것 통과 시 /imt-deploy
master 포함 prod 반영 완료 브랜치 삭제 가능
test(구버전) 최신화했는데 test 에 재병합 안 함 test 에 재병합
⚠ master 뒤처짐 드리프트 누적 /imt-sync feat

이게 v4 의 핵심이다. "브랜치 = 승격 단계"가 아니라 "어디에 merge 됐나 = 그 기능의 현재 단계". 사본 브랜치(-dev, -test)가 하나도 없다는 것도 확인해 두자.

속을 보는 법 — 칸반은 어떻게 계산되나

목적지마다 두 단계로 묻는다. tip 만 보면 안 된다 — /imt-sync feat로 최신화하면 tip이 앞으로 가서 어느 목적지에도 없게 되고, 칸반이 그 기능을 "아무 데도 안 갔다"고 보고한다 (TESTING_V4.md F10 — 실제로 이 함정에 빠졌다).

# 최신까지 들어갔나
git merge-base --is-ancestor origin/<feature> origin/test

# 구버전이라도 들어갔나
git rev-list origin/master..origin/<feature> \
  | while IFS= read -r c; do git merge-base --is-ancestor "$c" origin/test && break; done

# 이 커밋이 어디 있나 (같은 SHA 가 여러 곳에 있는 것을 눈으로)
git branch -r --contains $(git rev-parse origin/<내-feature>)
#   → origin/dev  origin/test  origin/master     복사가 아니라 각각 merge 됐다

이 확인은 실습 A를 끝낸 뒤 본인 feature 브랜치로 실행한다. 시작점에는 feature 브랜치가 없다.

2. 실습 A — 한 기능을 끝까지 (기본 사이클)

실제 배포 워크플로가 4회 돈다. 합쳐서 8~10분. 급하면 이 실습만 해도 핵심은 다 만진다.

날짜(MMDD)는 목표 배포일이다. 아래는 0821 / IMTDEV-5001 예시 — 본인 티켓 번호로 바꿔서 하자.

A-1. feature 시작

Claude Code / Codex

Claude Code: /imt-feature IMTDEV-5001 audit-filter 0821
Codex:      $imt-feature IMTDEV-5001 audit-filter 0821

→ 0821/YH/IMTDEV-5001-audit-filter 를 origin/master 에서 만든다. 네이밍 규칙 검증과 rerere 확인을 같이 해 준다.

속을 보는 법
git fetch origin --quiet
git checkout -b 0821/YH/IMTDEV-5001-audit-filter origin/master

agent workflow가 대신 막아 주는 것:

  • 분기원이 항상 origin/master — dev/test/release 분기는 금지(규칙 4)
  • 사본 명명 금지 — ...-dev, ...-test 같은 이름(규칙 1)
  • 혼합 명명 금지 — release-2.13.0-0819 처럼 버전+날짜 섞기

코드를 쓴다. 파일 하나 추가 + FeatureRegistry.register() 에 한 줄. 여기가 의도된 충돌 지점이다 — 모든 feature 가 같은 자리에 줄을 넣으므로 두 기능이 동시에 진행되면 반드시 부딪힌다.

        // ↓ feature 브랜치는 이 아래에 한 줄 추가한다 (여기가 충돌 지점)
        features.add("audit-filter");          // ← 이 줄

./gradlew -q build && java -cp build/classes/java/main com.ti.Main   # 등록 확인
git add -A && git commit -m "feat: IMTDEV-5001 감사 로그 기간 필터 추가"

커밋 메시지는 Conventional Commits. feat: 는 minor, fix: 는 patch. 이게 나중에 발급될 버전 번호를 결정한다.

A-2. dev — 연동 사전 확인 (선택)

test QA로 넘기기 전에 다른 기능과 붙여 봐야 할 때 수행한다. 파이프라인 밖이라 merge는 선택이며, 연동 확인이 필요 없다면 A-3으로 바로 간다.

속을 보는 법
git checkout dev && git reset --hard origin/dev
git merge --no-edit origin/master                     # 먼저 forward merge
git merge --no-ff --no-edit 0821/YH/IMTDEV-5001-audit-filter
git push origin dev            # push 하면 DEV 배포가 자동으로 돈다

이미지 태그는 sha-<커밋7자리>. "무슨 기능이 들어 있나"로만 읽는 환경이다.

연동 확인을 마쳤으면 feature 브랜치로 돌아간 뒤 QA 단계로 진행한다.

git checkout 0821/YH/IMTDEV-5001-audit-filter

A-3. test — QA 게이트 (본 리뷰가 여기다)

Claude Code / Codex (feature 브랜치에서)

/imt-test    또는    $imt-test

→ test PR을 만들고 merge한 뒤, test 배포 워크플로를 실행한다. 배포는 되돌리기 어려우므로 실행 전 승인을 받는다.

속을 보는 법
git push -u origin 0821/YH/IMTDEV-5001-audit-filter
gh pr create -R trial-informatics/git-branch-strategy-sandbox \
  --base test --head 0821/YH/IMTDEV-5001-audit-filter \
  --title "feat: IMTDEV-5001 감사 로그 기간 필터" --body "QA 대상. 본 리뷰 지점."
gh pr merge <번호> -R trial-informatics/git-branch-strategy-sandbox --merge
gh workflow run test-build-deploy.yml -R trial-informatics/git-branch-strategy-sandbox --ref test

--merge 다. --squash/--rebase 는 레포 설정에서 아예 막아 뒀다(금지규칙 8). PR 화면에 Squash 버튼이 없는 것도 확인해 보자 — 도구가 아니라 이게 최후 방어선이다.

충돌이 있으면 GitHub 버튼으로 못 닫는다. → 실습 B.

test도 dev도 버전이 없다. QA를 통과해도 배포일이 미정이면 여기 머문다 — 그게 정상이다.

A-4. release — UAT 조립대

Claude Code / Codex

Claude Code: /imt-release 0821 0821/YH/IMTDEV-5001-audit-filter
Codex:      $imt-release 0821 0821/YH/IMTDEV-5001-audit-filter

→ release-0821을 만들고 이번에 배포할 기능만 모은다. 다른 커밋이 잘못 섞이지 않았는지, 최신 master를 기준으로 만들었는지 확인한 뒤 UAT 배포를 실행한다. 날짜나 기능 브랜치를 생략하면 test에 대기 중인 기능을 보여주고 무엇을 배포할지 묻는다.

속을 보는 법
git checkout -b release-0821 origin/master
git merge --no-ff --no-edit origin/0821/YH/IMTDEV-5001-audit-filter

--no-ff 를 빼먹으면 fast-forward 되어 merge 커밋이 안 생긴다(금지규칙 8 위반). agent workflow는 이걸 항상 붙인다. 손으로 하면 빠뜨린다 — 실제로 그랬다.

agent workflow가 대신 하는 배포 전 점검 두 가지:

# ① orphan 검출 — release 에 직접 커밋한 게 없나 (금지규칙 6)
#    --not 에 이번 배포분 feature 도 넣어야 한다. 안 넣으면 feature 커밋이 그대로 잡힌다 (F5)
git log release-0821 --not origin/master \
  origin/0821/YH/IMTDEV-5001-audit-filter --no-merges --oneline    # 출력 없어야 정상

# ② master 가 ancestor 인가 — UAT 워크플로 가드가 이걸 본다
git merge-base --is-ancestor origin/master release-0821 && echo OK

git push -u origin release-0821
gh workflow run uat-build-deploy.yml -R trial-informatics/git-branch-strategy-sandbox --ref release-0821

끝나면 배포 원장이 태그로 남는다. Actions 로그는 90일이면 사라지지만 annotated 태그는 영구다.

git fetch origin --tags --quiet
git show $(git tag -l 'uat-v*' --sort=-creatordate | head -1)

UAT deploy — 1.5.0 (rc)
env      : uat
branch   : release-0821
commit   : <sha>
digest   : sha256:...
jdk      : ...        ← 고정하지 않고 기록한다. digest 가 어긋나면 여기서 원인을 찾는다
base-dig : sha256:...

uat-v1.5.0-rc.1 의 버전은 예보(forecast) 다 — "이대로 나가면 1.5.0 이 된다". 확정은 prod 에서만 일어난다.

A-5. master — prod 배포

Claude Code / Codex

/imt-deploy release-0821    또는    $imt-deploy release-0821

→ 조립 PR 1건을 만들고 4.1절 정합성 판독을 한 뒤, 최종 승인을 받고 나서만 merge 한다. 승인 게이트가 이 agent workflow의 핵심이다.

속을 보는 법

단건이면 조립 브랜치를 만들지 않는다(fast path). 여러 개면 assemble/{MMDD} 를 만들어 묶는다 — PR 1건 = 배포 1회이기 때문이다. feature 별로 PR 을 따로 올리면 배포가 N회 돈다.

# 묶음 배포일 때
git checkout -b assemble/0821 origin/master
git merge --no-ff <feature1>
git merge --no-ff <feature2>
git push -u origin assemble/0821

gh pr create --base master --head <assemble 또는 feature> --title "Release 0821 — ..."

정합성 판독(4.1절) — 비교 대상은 master 가 아니라 조립 결과물이다.

git diff release-0821 assemble/0821          # 묶음
git diff release-0821 origin/<feature>       # fast path
  • 비어 있음 → release 와 배포분이 같다. 안전
  • 제외분만 → 의도적 제외 (실습 D)
  • 그 외 → 충돌을 다르게 풀었거나 forward merge 누락 → 중단 (실습 E)

master 와 비교하면 배포 전에는 배포분 전체가, 배포 후에는 chore(release) 가 만든 version.yml·CHANGELOG.md 가 떠서 "비어 있음"이 나올 시점이 없다(F8).

merge 하면 prod 배포가 자동으로 돈다. 확인할 것은 두 줄이다.

✅ merge commit (부모 2개) — same-SHA 유지
✅ digest 일치 — UAT(uat-v1.5.0-rc.1)에서 검증한 이미지가 그대로 나간다

이 두 줄이 v4 + digest 추적의 결론이다. 첫 줄은 Squash 되지 않아 feature 의 SHA 가 master 에도 그대로 있다는 뜻이고, 둘째 줄은 UAT 에서 검증한 그 이미지가 나갔다는 뜻이다 — 사람이 비교한 게 아니라 워크플로가 uat-v* 태그를 훑어 자동 판정했다.

A-6. 배포 후 정리

Claude Code / Codex

Claude Code: /imt-sync env
Codex:      $imt-sync env

→ 먼저 배포가 끝난 release와 feature를 찾아 삭제 후보로 보여주고 승인을 묻는다. 승인한 브랜치만 정리한 뒤, 남아 있는 test/release/dev에 최신 master를 반영한다. test에서 대기 중인 feature는 삭제하지 않는다.

속을 보는 법
# 1. 삭제 후보만 확인 — 아직 삭제하지 않는다
git fetch origin --prune --quiet
git log origin/0821/YH/IMTDEV-5001-audit-filter \
  --not origin/master --no-merges --oneline
# 출력이 없으면 "삭제 후보: 0821/YH/IMTDEV-5001-audit-filter"
git log origin/release-0821 --not origin/master --no-merges --oneline
# 출력이 없으면 "삭제 후보: release-0821"

# 2. 위 목록을 보여주고 승인받은 뒤에만 삭제
git checkout master
git push origin --delete release-0821 0821/YH/IMTDEV-5001-audit-filter

# 3. 남아 있는 환경만 최신화
git checkout dev && git merge origin/master && git push origin dev
gh pr create --base test --head master \
  --title "chore: forward merge master into test" \
  --body "배포 후 기준선 갱신"

release는 사이클 1회용이지만 UAT 증적은 uat-v* 태그에 영구 보존된다. 삭제 후보 중 일부만 승인하거나 전부 거부해도 된다.

삭제 판단에서는 merge commit을 제외한다. 배포 과정에서 생긴 merge commit만 남아 있다면 미배포 코드가 남은 것이 아니다. 그래서 feature와 release 모두 --no-merges로 확인한다. 같은 이유로 git branch -d가 거부하더라도 그것만 보고 삭제를 중단하지 않는다. master에 없는 일반 커밋이 없고 사용자가 승인했다면 해당 로컬 브랜치는 git branch -D로 정리할 수 있다.

origin/master 를 쓰는 것에 주의. 로컬 master 는 fetch 만으로 갱신되지 않는다. git merge master 라고 쓰면 낡은 로컬 master 를 merge 해서 조용히 no-op 이 된다. (검증 중 두 번 물렸다.)

forward merge 를 빼먹으면 다음 배포의 4.1절 판독이 오염된다 → 실습 E.

여기까지가 기본 사이클이다. 아래는 곁가지 시나리오다.

3. 실습 B — 충돌과 rerere

핵심 질문: v4 는 같은 feature 를 목적지마다 따로 merge 하는데, 충돌도 목적지 수만큼 풀어야 하나?

기능 두 개를 만들어 둘 다 FeatureRegistry 같은 자리에 줄을 넣는다 (/imt-feature 두 번). A 를 test 에 먼저 넣으면 깨끗하고, B 는 충돌한다.

/imt-test 가 충돌을 감지하면 로컬 해결로 안내한다. GitHub 버튼으로는 닫을 수 없다 — rerere 캐시는 클론 로컬에만 있어서 GitHub 서버가 쓸 수 없다.

$ gh pr view <번호> --json mergeable,mergeStateStatus
mergeable=CONFLICTING   state=DIRTY

$ gh pr merge <번호> --merge
X not mergeable: the merge commit cannot be cleanly created.

로컬에서 풀고 push 하면 GitHub 이 그 PR 을 MERGED 로 자동 처리한다.

그다음 같은 B 를 release·assemble 에 merge 해 보자. /imt-release → /imt-deploy 순서로 가면 된다.

CONFLICT (content): Merge conflict in .../FeatureRegistry.java
Resolved '.../FeatureRegistry.java' using previous resolution.     ← 이 줄!

사람은 한 번만 풀고 나머지는 자동이다. 결과가 같은지는 느낌이 아니라 tree SHA 로 확인한다 (/imt-deploy 의 정합성 판독이 이걸 한다).

rerere 자동 해결은 눈으로 검증한다. /imt-sync 가 이걸 명시적으로 지시한다. 잘못 학습된 기록이면 git rerere forget <파일> 후 다시 푼다. 실제 검증에서는 서로 다른 두 기능의 등록 줄이 각각 올바르게 들어갔다. 텍스트를 맹목적으로 복사하는 게 아니다. 그래도 자동 해결 결과는 매번 눈으로 확인한다.

ls .git/rr-cache | wc -l          # 학습된 해결 개수

이 캐시는 push·pull 로 전파되지 않는다. 그래서 v4 에 "한 기능의 merge 는 담당자가 4곳 다 한다"는 규칙이 있다. 중간에 사람이 바뀌면 처음부터 다시 푼다.

4. 실습 C — 대기와 추월 (칸반)

가장 흔한 상황이고, v3 에서 표현할 수 없었던 것이다.

  1. 기능 A·B 를 둘 다 /imt-test (QA 통과)
  2. B 만 /imt-release → /imt-deploy
  3. A 는 test 에 그대로 둔다

/imt-status 로 A=test, B=test master 로 보이는지 확인한다. prod 앱 출력에 A 가 없는 것도 배포 로그에서 확인할 수 있다.

A 가 대기하는 동안 B 배포가 막히지 않는다 — 이게 v4 가 고치려던 핵심이다.

5. 실습 D — 배포에서 제외 → 재조립 (4.5절)

A+B 로 UAT 를 통과했는데 막판에 B 를 빼고 A 만 내보내려는 상황이다.

문제: prod 에 뜰 조합은 master + A 인데, UAT 는 master + A + B 를 봤다. 그 조합은 검증된 적이 없다.

Claude Code / Codex

/imt-deploy release-0821          → 재검증 경고로 중단해야 정상
/imt-release 0821-v2 <A 만>        → -v2 재조립 + uat 재검증
/imt-deploy release-0821-v2

/imt-release 가 4.5절 예외("명백히 독립")를 판정할 근거를 제시한다.

속을 보는 법 — 독립성 판정
# 세 점(...) 이다. 두 점으로 쓰면 좌변이 master tip 이 되어 분기 이후 master 커밋까지 섞이고,
# 어떤 두 기능이든 "겹친다"는 결론이 나온다 (검증 중 실제로 이 실수를 했다)
git diff --name-only origin/master...origin/<A> | sort > /tmp/a.txt
git diff --name-only origin/master...origin/<B> | sort > /tmp/b.txt
comm -12 /tmp/a.txt /tmp/b.txt      # 겹치는 파일 = 독립성 반증

판정은 두 기능이 아직 master 에 없을 때 한다. 한쪽이 이미 배포됐으면 목록이 비어 "겹침 없음 = 독립"이라는 잘못된 통과가 나온다.

-v2 는 master 에서 새로 만든다 — 그동안 나간 hotfix 도 자동으로 들어온다. 재조립이 forward merge 를 겸하는 셈이다.

digest 가 rc.1 과 달라진 것을 확인하자. 범위가 바뀌었으니 당연하고, 이것이 "재검증 없이 내보내면 안 되는" 이유의 가장 시각적인 증거다.

git tag -l 'uat-v*' --sort=creatordate | tail -2
git show <rc.1> | grep digest      # sha256:4f34...
git show <rc.2> | grep digest      # sha256:26a6...   다르다

배포 후 판독은 제외분 B 만 보이면 정상이다("의도적 제외").

6. 실습 E — hotfix (test 우회) + forward merge 를 빼먹으면

hotfix 는 전용 agent workflow가 없다. master 에서 hotfix/{설명} 을 만들어 master PR 로 직행한다 — test 를 건너뛰므로 본 리뷰가 master PR 로 옮겨 온다. fix: 이므로 patch bump 다.

git checkout -b hotfix/token-mask origin/master
# 최소 변경. FeatureRegistry 는 건드리지 않는다
git commit -am "fix: 감사 로그 토큰 평문 노출 차단"
git push -u origin hotfix/token-mask
gh pr create --base master --head hotfix/token-mask --title "hotfix: ..." --body "test 우회. 본 리뷰는 이 PR 에서."

배포 후 /imt-sync env를 일부러 건너뛰고 열린 release의 정합성 판독을 해 보자.

내 배포분과 무관한 hotfix 코드가 한 diff 에 섞여 나온다. 배포 담당자는 "이게 내가 내보내려는 것인가"를 구분할 수 없다 — 4.1절 판독이 무력해지는 순간이다. /imt-sync env를 실행하면 제외분만 남는다.

가드는 언제 도는가

hotfix 이후 낡은 release 로 UAT 를 다시 돌리면 워크플로가 막는다.

::error title=낡은 소스::release-0821 에 최신 master가 반영되지 않았습니다.

단 UAT 배포 워크플로를 실행할 때만 돈다. 이미 UAT 를 통과한 뒤 배포로 직행하면 가드가 다시 돌지 않고, 그 구간의 유일한 신호가 4.1절 diff 다. 이것이 forward merge 를 의무로 둔 실질적 근거다.

7. 실습 F — test 리셋 (7절)

test 가 오래 쌓여 읽을 수 없게 되면 버리고 다시 만든다. v4 에서 유일하게 버려도 되는 브랜치다. 전용 agent workflow는 없다 — /imt-status 또는 $imt-status로 상태를 보고 절차를 수동으로 밟는다.

# 얼마나 쌓였나
git log origin/test --not origin/master --merges --oneline | wc -l

F-1. 보호 일시 해제 (필수)

리셋은 non-fast-forward 라 force push 가 필요한데 test 는 막혀 있다. 관리자도 우회하지 못한다 — enforce_admins:false 는 PR 요구만 면제한다(F6).

./scripts/repo-settings.sh unlock-test

F-2. archive → orphan 검출 → reset → 재병합

# ① 되돌릴 수 있게 고정
git tag -a archive/test-$(date +%Y%m%d) origin/test -m "test 리셋 전 보존 (7절)"
git push origin refs/tags/archive/test-$(date +%Y%m%d)

# ② 무엇을 잃는지 먼저 본다 (feature 브랜치도 --not 에 넣는다)
git log origin/test --not origin/master \
  $(git for-each-ref --format='%(refname:short)' refs/remotes/origin | grep -E '^origin/[0-9]{4}/') \
  --no-merges --oneline
git branch -r --contains <sha>      # origin/test 하나만 나오면 확정 orphan

# ③ 리셋
git checkout test && git reset --hard origin/master

# ④ 대기분을 원본 feature 에서 재병합
#    zsh 는 변수를 단어분리하지 않는다 → 파이프 + while read
printf '%s\n' <대기1> <대기2> | while IFS= read -r b; do
    git merge --no-ff --no-edit "origin/$b"     # 충돌은 rerere 가 자동 해결
  done
git push -f origin test:refs/heads/test

F-3. 원복 (잊지 말 것)

./scripts/repo-settings.sh lock-test

F-4. 확인

대기 기능의 SHA 가 리셋 전후 같아야 한다 — 원본 feature 에서 재병합했으므로. 직접 커밋이 있었다면 어느 브랜치에도 없고 archive 태그에만 남는다.

"소실"이 회수 불가는 아니다. archive 태그로 내용을 읽을 수 있고, 살리려면 master 에서 feature 를 파고 cherry-pick 한다 — 애초에 했어야 할 경로다.

8. 치트시트

agent workflow가 먼저다. 아래는 workflow가 안 되는 상황이나 원리 확인용.

# 이 기능이 어디까지 갔나
git branch -r --contains <sha>

# 목적지에 master 대비 무엇이 들어 있나
git log origin/test --not origin/master --merges --oneline

# orphan (직접 커밋) 검출 — feature 브랜치를 반드시 제외한다
git log origin/test --not origin/master \
  $(git for-each-ref --format='%(refname:short)' refs/remotes/origin | grep -E '^origin/[0-9]{4}/') \
  --no-merges --oneline

# 배포 전 정합성 (4.1절) — master 가 아니라 조립 결과물과 비교
git diff release-{MMDD} assemble/{MMDD}
git diff release-{MMDD} origin/master -- . ':!version.yml' ':!CHANGELOG.md'   # 사후 확인

# 배포 횟수 (조립 PR 1건 = 1회인지)
gh run list -R trial-informatics/git-branch-strategy-sandbox --workflow=prod-build-deploy.yml -L 20

# 배포 원장
git tag -l 'uat-v*' --sort=-creatordate
git show uat-v1.4.0-rc.2

# 레포 설정
./scripts/repo-settings.sh show

9. 함정 모음 — 실제로 물린 것들

대부분 agent workflow를 쓰면 안 만난다. 손으로 하다가 물린 것들이다.

함정 증상 대응
zsh 단어분리 for b in $VAR 가 리스트를 한 덩어리로 넘긴다. 에러 없이 조용히 틀린다 파이프 + while IFS= read -r. $(...) 명령치환은 zsh 에서도 분리되므로 괜찮다
zsh : 모디파이어 git push origin "$b:refs/heads/$b" 가 masterefs/heads/master 로 망가진다 변수 뒤에 : 가 오면 반드시 ${b}:...
zsh echo - 하이픈이 옵션으로 먹혀 빈 문자열이 된다. 따옴표를 씌워도 같다 표 마커로 . 를 쓰거나 printf -- '-'
set -e 가 && 를 안 잡는다 checkout && reset 에서 checkout 이 실패해도 뒤 명령이 계속 돌아 엉뚱한 브랜치에 커밋된다 브랜치 전환은 한 줄씩. 전환 후 git rev-parse --abbrev-ref HEAD 로 확인
git add -A 가 무관한 편집을 삼킨다 작업 중이던 다른 파일이 merge 커밋에 함께 들어간다 커밋 전 git status 확인. 아깝다 싶으면 git stash
로컬 master 가 낡음 git merge master 가 조용히 no-op. forward merge 했다고 착각한다 origin/master 를 직접 쓴다
--no-ff 누락 fast-forward 되어 merge 커밋이 안 생긴다 (금지규칙 8 위반) /imt-release·/imt-deploy 는 항상 붙인다. 손으로 하면 빠뜨린다
커밋 전 reset --hard 편집 중이던 내용이 날아간다 git status 먼저. 날렸으면 git reflog 로 회수
force push 가 막힘 ! [remote rejected] ... protected branch hook declined ./scripts/repo-settings.sh unlock-test → 작업 → lock-test
orphan 검출 거짓 양성 정상 사이클에서도 feature 커밋이 잡힌다 --not 에 feature 브랜치를 넣는다 (F5)
4.1절 diff 가 안 비워짐 배포 전엔 배포분, 배포 후엔 version.yml·CHANGELOG.md 가 뜬다 조립 결과물과 비교하거나 뒤처리 파일을 제외 (F8)
독립성 판정에 두 점 어떤 두 기능이든 "겹친다"고 나온다 master...feature 세 점. 그리고 배포 전에 판정
충돌 PR 을 UI 로 merge not mergeable: the merge commit cannot be cleanly created 로컬에서 풀고 push. rerere 는 로컬에서만 먹는다
