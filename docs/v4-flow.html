IMT Git Branch 전략

v4 확정 · 2026-08-14

브랜치는 승격 파이프라인이 아니다.
4개의 독립 목적지다.

v3까지는 기능이 dev → test → uat → prod 로 올라간다고 생각했다. 그래서 목적지마다 사본 브랜치를 만들고, 같은 기능이 환경마다 다른 SHA를 갖게 됐다. v4는 방향을 뒤집는다 — 브랜치 하나를 만들고, 보내고 싶은 곳에 그 브랜치를 merge한다.

하나의 기능 = 하나의 브랜치 = 동일한 커밋(SHA)이 dev / test / release / master 에 각각 독립 merge된다.
어디까지 merge했나 = 그 기능의 현재 단계. 그래서 브랜치 목록이 곧 칸반 보드가 된다.
01

시나리오 2 — 대기와 추월

v4에서 가장 흔한 패턴이자, v3에서 표현할 수 없었던 상황이다. featA는 QA를 통과했지만 배포일이 미정이고, featB는 배포가 확정됐다. featA가 test에서 기다리는 동안 featB가 먼저 나간다. 단계를 눌러 보거나 ← → 로 넘겨라.

    02

    v3에서 무엇이 틀렸나

    두 그림의 차이는 브랜치 개수가 아니라 SHA가 몇 개인가다. 왼쪽은 목적지마다 사본을 만들어 "같은 기능"이 서로 다른 커밋 4개가 된 상태다 — UAT에서 검증한 것이 prod에 나간 것과 다르다.

    ✕ 사본 브랜치 (금지)

    cherry-pick·재작성으로 트리가 미묘하게 갈라진다. "UAT에서 통과했다"는 증적이 성립하지 않는다.

    ✓ same-SHA (v4)

    브랜치 1개를 네 곳에 merge한다. 커밋은 하나뿐이므로 UAT 증적이 prod에 그대로 유효하다.

    04

    왜 조립 PR 1건인가

    prod 트리거가 pull_request closed(merged) 이라서 PR 1건 = 배포 1회다. 이 사실 하나가 묶음 배포 방식을 결정한다 — v3의 "묶음 push 1회 = 배포 1회"는 이 트리거에서 아예 동작하지 않는다.

    ✕ feature별 PR 2건

    Blue-Green이 중첩된다. concurrency group이 줄은 세워주지만 배포 횟수는 줄이지 않는다.

    ✓ 조립 PR 1건

    assemble/{날짜}에 feature merge들을 모아 master로 PR 1건. 트리는 동일하고 배포만 1회다. 내용이 release-{날짜}와 같아야 정상이며, 배포에서 기능을 뺄 때는 여기서 골라내지 않고 release-{날짜}-v2로 재조립 + UAT 재검증한다.

    환경별 트리거 (v4 12절 목표 상태)

    환경트리거소스왜
    dev⚡ push 자동dev연동 확인은 빠를수록 좋다
    test▶ dispatchtestQA가 검증 시작 시점을 통제 — 검증 중 다른 merge에 덮이지 않는다
    uat▶ dispatchrelease-{날짜}release가 동시에 여러 개 열린다. push 자동이면 검증 중인 UAT를 덮어쓴다
    prod⚡ PR merged 자동masterUAT가 진짜 게이트다. 검증한 소스를 그대로 내보낸다 (+ concurrency group)
    05

    금지 규칙

    대부분 "역방향" 또는 "통째"를 막는 규칙이다. 둘 다 미배포 기능을 master로 끌고 들어오는 경로다.

    ✕
    타겟별 사본 브랜치
    -dev -test -uat 접미사 금지. 사본이 곧 SHA 분기다.
    ✕
    feature에 dev/test/release merge
    역방향 오염. 당겨오는 건 git merge master 만.
    ✕
    test / release를 어디로든 merge
    둘 다 목적지 전용. master가 받는 건 feature 단위 merge 또는 그걸 모은 조립 브랜치뿐이다 (release 통째 merge·FF 금지).
    ✕
    release를 다음 release로 흡수
    fold-in 금지. 미배포분은 원본 feature에서 새 release로 다시 merge.
    ✕
    dev/test/release에서 feature 분기
    항상 master에서. 아니면 미배포 코드를 업고 시작한다.
    ✕
    공유 브랜치 rebase
    git merge master로 대신한다.
    ✕
    dev / test / release에 직접 커밋
    모든 코드는 feature 경유. dev·test는 리셋 때 소실되고, release는 통째 merge 시 미검증 코드가 조용히 prod로 들어간다.
    ✕
    Squash / Rebase merge
    전 경로 Merge Commit. same-SHA가 깨지면 모델 전체가 무의미해진다.
    ✕
    master에 UAT 미통과분 merge
    master가 항상 prod와 같아야 hotfix 기준선이 유효하다.
    ✕
    제외 배포 후 재검증 생략
    A+B로 UAT 통과 → A만 배포하면 master+A는 미검증 조합. -v2 재조립이 기본.
    06

    Claude Code 커맨드 — 어떻게 쓰나

    v4 본문의 권장 도구(부록 B). 규칙을 .claude/에 스킬 1개 + 커맨드 6개로 옮긴 것.
    팀 공용으로 쓰려면 .claude/의 스킬·커맨드를 레포에 체크인해야 clone만으로 동작한다 (settings.local.json과 *.lock은 로컬 전용이므로 제외). 07절 참조.
    imt-git-flow는 스킬이라 아무것도 안 쳐도 브랜치·merge·배포 얘기가 나오면 배경에서 참고된다. /로 시작하는 6개는 직접 입력해 실행하는 커맨드다.
    하루 흐름: /imt-feature → 커밋 → /imt-test → (대기) → /imt-release → /imt-deploy → /imt-sync. 막히면 /imt-status.

      강제의 한계

      이 도구는 Claude를 통할 때만 유효하다 — 터미널 직접 git push나 GitHub UI의 Squash 버튼은 못 막는다. 진짜 강제는 GitHub 설정(Squash/Rebase merge 비활성, branch protection, required PR)이다. 커맨드는 "올바른 길을 가장 쉬운 길로" 만드는 생산성 계층이지 최후 방어선이 아니다.

      07

      확정 기록 — 2026-08-14

      v4는 확정됐다. 초안 단계의 보류 항목 2건(B2·부록 A)과 샌드박스 검증에서 나온 4건(F1–F4)이 모두 닫혔다. 근거·재현 스크립트는 TESTING_V4.md에 있다.

      ●
      B2 — dev merge = 선택
      연동이 필요할 때만 merge한다. 의무 merge는 test / release / master 3회.
      ●
      부록 A — epic(버전 트랙) 미도입
      버전 트랙은 현행 방식 유지, 운영안은 참고로만 보존. 단 release- prefix 금지는 유지 → 버전+날짜 혼합 명명(release-{버전}-{날짜})은 rename 또는 마감 후 삭제 대상.
      ●
      F1 — 조립 브랜치 유지
      prod 트리거가 PR 1건 = 배포 1회라서 묶음 배포에는 조립 브랜치가 필요하다. release-{날짜}와 내용이 중복되는 것은 수용한다(실측: 두 경로의 트리 SHA 동일). 제외는 -v2 재조립 + UAT 재검증만으로 한다.
      ●
      F2 — 조립 브랜치 명명 신설
      3절 명명 규칙에 assemble/{월일} 추가. 묶음 배포 시에만 만들고 배포 후 삭제. 단건이면 만들지 않는다(fast path).
      ●
      F3 — 금지 규칙 7에 release 추가
      "dev / test / release-{날짜}에 직접 커밋 금지"로 개정. 실측 근거: release 직접 커밋은 통째 merge 시 아무 신호 없이 prod로 들어간다.
      ●
      F4 — 금지 규칙 4 근거 재작성
      FF 논거는 FF에만 한정하고, 실제 근거를 ① orphan 격리(실측) ② 기본값 안전성으로 다시 썼다. rerere는 근거가 아니라 "통째와 동일한 트리를 보장하는 장치"로 위치를 옮겼다.

      남은 것은 적용이다 — 13절 전환 체크리스트

      문서가 확정돼도 규칙이 저절로 강제되지는 않는다. 아래 ①~③은 확정과 함께 켜야 하는 강제 장치다 — 이게 없으면 v4는 권고에 그친다. 각 레포의 현재 적용 상태는 사내 문서(13절)에서 확인한다.

      항목해야 할 것안 하면
      GitHub merge 설정 ① Squash / Rebase merge 비활성. delete_branch_on_merge는 false 유지 same-SHA가 언제든 깨진다. 켜두면 test PR merge 때 feature가 삭제된다
      CI/CD ② prod concurrency group + 이미지 태그 버전/SHA 병행 Blue-Green 중첩. 환경명 고정 태그로는 "UAT에서 검증한 이미지 = prod 이미지" 증명 불가 (감사 요건)
      dev divergence ③ dev 1회 리셋 (orphan 검출 선행) divergence를 안고 시작하면 forward merge 규율이 성립하지 않는다
      열린 release 배포 끝난 release 삭제. 혼합 명명(release-{버전}-{날짜})은 rename release- prefix가 UAT 조립대 전용이라는 규칙이 흐려진다
      test 브랜치 다음 기능부터 test PR을 본 리뷰 지점으로 사용 개시 브랜치만 있고 QA 게이트가 실제로 돌지 않는다
      feature 네이밍 기존 브랜치 rename 강제 없이 신규부터 적용해 소진 일괄 rename은 진행 중인 PR을 깨뜨린다
      Claude Code 도구 팀 공용으로 쓸 거면 체크인 (스킬 1 + 커맨드 6만, settings.local.json·lock 제외) 개인 로컬 전용이라 clone만으로는 쓸 수 없다
